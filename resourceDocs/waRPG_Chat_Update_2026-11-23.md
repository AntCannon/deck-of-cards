## 1. Default constructor arguments and UUIDs

User has a `Card` data class with a UUID generated by default, along the lines of:

```kotlin
data class Card(
    val cardId: String = UUID.randomUUID().toString(),
    val rank: Rank,
    val suit: Suit? = null
)
```

To omit the generated ID when constructing a card, use named arguments:

```kotlin
Card(rank = rank, suit = suit)
Card(rank = Rank.LITTLE_JOKER)
Card(rank = Rank.BIG_JOKER)
```

`cardId` remains present and is generated automatically. A manually supplied ID overrides the default. Joker rank must be passed as `rank`, not `cardId`.

## 2. Pile subclasses and types

- Kotlin classes are final by default; `open class Pile` permits subclassing.
- A subtype such as `DiscardPile : Pile(...)` is normally declared outside the `Pile` class body, ideally in a separate file.
- A subclass is useful if its behavior differs; otherwise, a `PileType` enum can distinguish pile roles without creating subclasses.
- Proposed distinction:

```kotlin
enum class ContainerType { SHOE, DECK, PILE }
enum class PileType { HAND, DISCARD, STANDARD }
```

- Example `Pile` properties include `containerId`, `containerName`, `containerType`, `pileType`, and a card collection.
- Avoid conflating a nested enum class named `PILE` with an enum constant `ContainerType.PILE`.
- An open question was whether HAND should be a pile subtype or its own container type; no final decision was made.

## 3. Card counts and last-card access

The `CardContainer` interface can supply a computed getter:

```kotlin
val cardCount: Int
    get() = cards.size
```

Implementations inherit this default getter; no override is needed unless behavior differs. Access as `deck.cardCount`, not `deck.cardCount()`.

For the last card:

```kotlin
initialDeck.cards[initialDeck.cardCount - 1]
// Simpler:
initialDeck.cards.last()
// Safe for empty list:
initialDeck.cards.lastOrNull()
```

The `cards` list must be indexed, not the integer `cardCount`. Kotlin uses zero-based indexes.

## 4. Tracking card containers, locations, and movements

The user wants **all card movements tracked**, including container registry, current card locations, and historical movements.

Suggested structures:

```kotlin
val containers: MutableMap<String, CardContainer> = mutableMapOf()
val cardLocations: MutableMap<String, CardLocation> = mutableMapOf()
val movementHistory: MutableList<CardMovement> = mutableListOf()
```

Possible data models:

```kotlin
data class CardLocation(
    val cardId: String,
    val containerId: String,
    val position: Int
)

data class CardMovement(
    val movementId: String = UUID.randomUUID().toString(),
    val cardId: String,
    val fromContainerId: String?,
    val toContainerId: String?,
    val fromPosition: Int?,
    val toPosition: Int?,
    val timestamp: Instant = Instant.now()
)
```

A centralized `CardMovementManager` should coordinate movements, check source/destination/card validity, update positions, and record history. A card's `cardId` remains stable through movement. Shuffling and reordering may need to be recorded as movements as well.

**Important design caution:** Container lists and a separate location map duplicate information. For the initial learning implementation, prefer container contents as the source of truth and derive locations when needed. Add a location index later if useful, ensuring it cannot diverge. Avoid exposing unrestricted mutable lists if all changes must be tracked.

## 5. Atomic transactions: all-or-nothing card moves

The user specifically proposed making changes on copies, checking for success, then publishing the final state only when the whole transaction succeeds. This is a valid approach.

Agreed conceptual flow:

1. Receive a movement request.
2. Validate card ownership, containers, positions, and rules.
3. Stage proposed changes in temporary/immutable state.
4. Verify all invariants, including card uniqueness and location consistency.
5. If any step fails, discard staged state; **original state remains unchanged**.
6. If everything succeeds, publish the new authoritative state once, including movement history.

Suggested typed results:

```kotlin
sealed class MoveResult {
    data class Success(val cardId: String) : MoveResult()
    data class Failure(val reason: MoveFailure) : MoveResult()
}

enum class MoveFailure {
    CARD_NOT_FOUND,
    SOURCE_NOT_FOUND,
    DESTINATION_NOT_FOUND,
    INVALID_MOVE,
    STATE_CONFLICT
}
```

Internal Kotlin operations do not require HTTP status codes. A `sealed class` is suitable for success/failure. Result types alone do not ensure atomicity.

Suggested authoritative state model:

```kotlin
data class GameState(
    val containers: Map<String, List<Card>>,
    val cardLocations: Map<String, CardLocation>,
    val movementHistory: List<CardMovement>
)
```

The movement function should take an existing state and request, then return either a failure or a fully prepared replacement state. The caller commits by replacing the authoritative state reference **once**. Do not mutate several live containers sequentially after staging, because partial failures could corrupt state.

**Caveats:** Kotlin `data class.copy()` is shallow. Ensure nested collections and objects cannot mutate shared prior state. A single reference replacement is a suitable basic pattern under controlled single-threaded ownership; concurrent server transactions require synchronization, version checks/locking, and database transactions. Group multiple card moves into one transaction when an entire battle action must succeed together. Consider transaction IDs, sequence numbers, and state versions later.

## 6. Mobile versus server architecture

Discussion distinguished:

- **Offline Android:** UI, game rules, authoritative state, and local persistence on device.
- **Server-authoritative:** Android sends actions; server validates rules, updates authoritative state, and persists changes in database transactions. Client displays permitted results.

Core Kotlin card mechanics can be shared conceptually across both. A server may require authentication, request deduplication/idempotency, concurrency protection, persistence, and server time for idle rewards. No server framework is required for the first release. A pure Kotlin `game-core` module can later be used from Android and server code.

## 7. User's confirmed three-stage product direction (November 23)

This supersedes earlier brainstorming about premium currency in the *initial* release.

### WarPG I — First release: offline, single-player Android idle RPG

- Primary purpose: practice Kotlin and build/release a manageable game.
- Android-only; no required online server.
- **No premium currency.**
- Core gameplay: gain XP, play mini-games, fight battles, and engage in idle progression.
- Local game state and saves.
- Build simple mechanics before expanding scope.

### WarPG II — Second release: online, single-player idle RPG

- Online/server-based game.
- Storyline and deeper progression mechanics.
- Premium currency is included.
- Server-controlled state, player accounts, and persistence are likely requirements.
- Expand XP, skills, talents, idle systems, and other mechanics deliberately rather than implementing them all in version I.

### WarPG PvP — Separate competitive experience

- PvP is separate from the single-player development path.
- Matchmaking is a major architectural consideration.
- Some single-player mechanics may be unfair in PvP, so competitive balance and rules must be separately designed.
- Share basic engine mechanics where sensible, but do not force identical battle rules, progression, skills, or talents.

### Architecture direction

Separate **mechanics** (how a card moves, how state is updated) from **rules** (whether an action is allowed in a given game mode). A future `BattleRules` interface and different single-player/PvP implementations were discussed as illustrative examples, not an immediate requirement.

Proposed organization, conceptual only:

```text
WarPG/
  core/
    card/          Card, Rank, Suit
    container/     CardContainer, Deck, Pile
    movement/      CardMovement, CardMovementManager, MoveResult
    game/          GameState, BattleRules
  android/         UI and local storage
```

Start with packages in the current project; separate Gradle modules only when warranted.
